# Threat model for the contextual service

This document covers the v2 Python service and its web proxy. The older local CLI is a separate compatibility interface. The main security objective is to let untrusted vulnerability reports influence a reviewable hypothesis without granting authority over company files, infrastructure, policy, credentials, public disclosures or outbound destinations.

## Assets and trust boundaries

Sensitive assets include indexed source, source hashes and excerpts, deployment topology, owner mappings, company risk decisions, report contents, model credentials, integration credentials, the SQLite database and backups, operator tokens, and researcher receipt tokens.

External researchers and report text are untrusted. Code comments and repository text are also untrusted as model instructions, even when an approved repository supplies them. A compromised contributor can poison source context. Model output is untrusted structured data. Operators, the configured local repository roots, topology collectors and destination configuration hold authority; compromising any of those can invalidate the context and decisions.

The boundaries are: browser to allowlisted proxy; proxy to the fixed private service; researcher intake to the persistent queue; trusted collectors to the context store; evidence retrieval to the model boundary; model response to deterministic validation; private decision to public receipt; and approved event to a configured integration. Database organization scoping is defense in depth, not a supported shared multi-tenant hosting design.

## Attacks and implemented controls

| Attack | Implemented control | Remaining exposure |
| --- | --- | --- |
| Report or source comment instructs the model to accept a false report, expose secrets, change policy, or contact a URL. | Model has no tools; report and context are data; strict schema and exact source citation checks; public text and integration payloads are built independently. | Valid citations can still accompany an incorrect or manipulated interpretation. Source-backed primitives are provisional static hypotheses. |
| Researcher supplies a path, repository URL, shell payload or archive to make the server read or execute arbitrary files. | Intake schema accepts only title, description and an explicitly reportable asset. Repositories and topology come from operator configuration. Retired web verifier returns 410. | Administrators can still configure an overbroad repository root. Host compromise defeats process-level boundaries. |
| Approved repository contains symlinks, binary payloads, giant files or generated dependency trees. | Bounded scan and content size; generated/likely secret exclusions; descriptor-relative reads with `O_NOFOLLOW`; no execution, build or archive extraction. Over-budget full scans preserve the previous index. | Exclusions intentionally omit some evidence. Oversized or unreadable files are not a comprehensive index. Snapshot consistency across a repository changing during a scan requires a stable checkout supplied by the operator. |
| Hostile Python syntax exhausts parser resources or its call graph is mistaken for attacker reachability. | File-size, AST-node, processing-time and derived-object limits; syntax/resource failures remain explicit file metadata; `code_call` and `code_defines` have no movement capabilities and are excluded from runtime path logic. | Parsing remains in-process, so the checked time budget cannot preempt the parser itself. Lexical call resolution is deliberately incomplete and never proves runtime behavior. A separate resource-limited parsing worker would strengthen isolation. |
| One collector overwrites another collector's facts or two repositories share misleading paths. | Source ownership collision checks; tenant-scoped keys; transactional replacements; optional explicit `code_source_ids`; ambiguous unbound paths cannot supply evidence. | A trusted collector can still publish inaccurate facts within its own contribution. No signed collector attestations are implemented. |
| Old code, deployment facts or acceptance rules suppress a new vulnerability. | Stable content-derived graph revision, source refresh timestamps, freshness checks during analysis and periodic decision refresh, requeue on graph or policy change, expiring evidence-bound acceptances. | Freshness records collection time, not proof of deployed state. Sources are not continuously watched. Periodic refresh uses saved analysis rather than new source scans or runtime checks. A reused manifest revision can still contain incorrect operator assertions. |
| Unknown connectivity is interpreted as a functioning control, or a small primitive is ignored. | Edges explicitly distinguish observed, blocked and unknown. Only observed relationships grant movement; unmet prerequisites and latent primitives remain visible. | Missing graph facts cannot prove safety. Blocked declarations are trusted assertions, not independently tested controls; path logic is bounded and simplified. |
| A model invents evidence or grants capabilities on an unrelated asset. | Citation IDs, line ranges and literal quotes are checked against retrieved content hashes; primitive asset and capability scope are constrained. | Citation validation establishes provenance, not exploitability. Primitive composition can amplify an erroneous premise. Operator review remains necessary for material decisions. |
| Receipt lookup leaks another report or internal architecture. | Random 128-bit report IDs, separate high-entropy receipt tokens, stored receipt hashes, constant-time hash comparison, fixed status and safe outcome responses. | A stolen receipt can reveal its report's status and safe outcome. Public program asset IDs and names are intentional disclosure. There is no receipt recovery or revocation UI. |
| Stolen operator token changes context or exports private evidence. | Distinct operator and optional submission bearer tokens, minimum configured length, private operator endpoints, tab-memory token storage. | Tokens are shared static credentials without individual roles, MFA, per-user attribution or automatic rotation. Browser compromise, extensions, clipboard exposure and infrastructure logs remain relevant. |
| Report text becomes Slack mentions, external links, Jira markup or an attacker-selected webhook. | Only configured Slack/Jira destinations; limited generated metadata; Slack plain-text blocks and disabled unfurls; owner-to-account mapping; no report/model prose in delivery. | Administrator destination mistakes or credential theft remain possible. A proxy, DNS configuration or permitted destination may still be compromised. |
| Redirects or arbitrary destinations exfiltrate code or credentials. | Fixed model and backend configuration; disabled HTTP redirects; explicit external-model opt-in; HTTPS for external models and integrations; bounded responses and timeouts. | This is not a network firewall. The on-premises label is a configuration assertion. Deploy egress restrictions and protect environment/proxy/DNS settings to enforce the intended data boundary. |
| A graph change races with model completion or old delivery. | Analysis checks graph revision before and after evaluation; generation checks reject superseded results; mutation lock coordinates the single worker; stale pending events are cancelled. | Multiple service processes are unsupported. External delivery cannot be transactionally atomic with SQLite; duplicate messages remain possible. |
| Flooded reports exhaust memory, disk, model credits or worker availability. | 128 KiB API body limit, field bounds, peer-based submission rate limit, 1,000 queued/in-progress report cap, bounded graph/context/model output, finite delivery retries. | Rate limits are process-local. Behind the web proxy the service sees the proxy peer. Completed records and audit history have no automatic retention limit; long model calls and repeated re-analysis can still be expensive. |
| Untrusted text runs script in the operator browser or appears in logs. | React text rendering rather than report HTML execution; JSON proxy reconstructs responses; no-store headers; sanitized operational errors; server access logging disabled by its entry point. | Browser and reverse-proxy policies need deployment review. Indexed source and private model summaries can contain secrets despite these controls. |

The [OWASP AI Agent Security guidance](https://cheatsheetseries.owasp.org/cheatsheets/AI_Agent_Security_Cheat_Sheet.html) describes direct and indirect prompt injection, memory poisoning, data exfiltration and authority abuse. Gavel addresses these with boundaries around the model, rather than treating a suspicious phrase detector as an authorization control. A report about prompt injection is legitimate data and must not automatically become an invalid vulnerability.

## Data handling and authorization assumptions

The service deliberately persists reports and source excerpts, unlike the original zero-retention positioning. SQLite, its WAL/SHM files, backups and operator exports require restricted filesystem access and the organization's retention policy. The service does not encrypt database contents itself. Its command entry point uses a restrictive umask; embedding the app in another process does not establish that process's filesystem policy.

Likely secret filenames and private-key blocks are skipped, but secret detection is imperfect. Credentials embedded in ordinary source or configuration can reach the local database and configured model. The model's instruction not to quote secrets is not a reliable redaction boundary. Use scoped read-only checkouts and a model deployment approved for the data, then add a dedicated secret-classification/redaction layer before broader production ingestion.

Operator authentication authorizes private reads, topology changes, policy changes and delivery approval. The optional submission token is a separate shared program credential; it is not a researcher identity. A receipt token is limited to one report's public status and safe outcome. The proxy forwards supplied credentials but holds no administrator token. TLS termination, network exposure, origin policy and bearer-token hygiene remain deployment responsibilities.

Risk acceptance is an operator decision about a specific evidenced primitive, with a reason and expiry. It neither removes technical support nor establishes the absence of dangerous chains. The structure is informed by contextual remediation and applicability concepts in [CISA SSVC](https://www.cisa.gov/sites/default/files/publications/cisa-ssvc-guide%20508c.pdf) and [OpenVEX](https://github.com/openvex/spec/blob/main/OPENVEX-SPEC.md); this implementation claims no standards compliance.

## Explicit limits and next safeguards

There is no runtime verifier, exploit runner, automatic patcher or production probe. Submitted code is text and never executed. Introducing execution would require a new threat model: disposable isolated workers, no production credentials, default-denied network, explicit target authorization, CPU/memory/time/storage budgets, controlled artifact export, clean teardown and independently captured reproduction evidence. An ordinary container alone must not be assumed to contain hostile execution.

Before broad production use, prioritize SSO with per-user roles and auditable approvals; collector provenance and source-to-deployment binding; historical evidence retention; encryption and lifecycle controls; cost budgets and admission controls at the edge; external egress policy; and a red-team evaluation set for prompt injection, false refutation, false chains and evidence confusion. Use a single worker until durable leases and coordination are designed for multiple processes. Reconcile uncertain Jira/Slack outcomes rather than assuming the idempotency header prevents duplicate tickets.

Any claim that a finding is exploitable, not applicable or safely accepted should be reviewable against evidence and declared assumptions. [CVSS v4.0](https://www.first.org/cvss/v4.0/specification-document) provides a richer severity vocabulary than a single low/medium/high label, but neither a score nor Gavel's graph replaces evidence about this organization's actual deployment.
